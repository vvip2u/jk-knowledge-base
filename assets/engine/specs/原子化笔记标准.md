# 原子化笔记标准

> 一张卡片写多长、必须包含哪几段，以本文为准。核心判据只有一句：
> **脱离原上下文依然能被读懂，并直接指导行动。**

## 一、四条硬原则

### 1. 单一职责

一个原子知识点只解决一个问题、说明一条规则或演示一个步骤。
「为什么做」「怎么做」「事故检讨」分属三个层次，应拆成独立文件，不要混在一篇里。

### 2. 自包含语境

严禁「如上文所述」「同步骤二」「点击它」这类依赖上下文的模糊指代。
必须保留关键主语与环境：把「点击它」写成「在配置中心点击【立即发布】」。

### 3. 结构化容器（五段缺一段即 FAIL）

| 段 | 写什么 |
| --- | --- |
| 问题定义（Context & Problem） | 发生了什么，或要达成什么目标 |
| 前提条件（Prerequisites） | 所需权限、依赖环境或前置知识 |
| 行动步骤（Action Steps） | 1、2、3 动宾结构的无歧义操作指令 |
| 预期结果与验证（Verification） | 如何证明操作成功 |
| 异常处置（Troubleshooting） | 报错代码及对应解决方案 |

### 4. 长度与粒度

- 人工阅读：单张原子卡片 **300–800 字**，支持 1 分钟内完成意图捕获；
- AI 向量化（RAG Chunk）：**256–512 Token**，中文约 400–800 字；
- 切片重叠 **10%–15%**，默认 `0.12`，避免语义被硬切断；
- 超出的部分不是「再写长一点」，而是**拆成第二张卡**。

## 二、文件名规则

- 一卡一文件，命名 `对象-动作-结果.md`，如 `CRM-客户去重-按手机号合并.md`；
- 不用空格，用 `-` 或 `_`；禁用 `\ / : * ? " < > |`；
- 文件名说清「这是什么」，不要用 `未命名`、`新建笔记`、`总结1`。

## 三、frontmatter 最低要求

至少覆盖五维（详见《元数据规范》），其中与原子化直接相关的三项：

```yaml
id: K-2026-002
title: CRM-客户去重-按手机号合并
confidence: 中
conf_src: [S-2026-006]
l1: 知识/卡片
l2: [实施顾问]
l3: [SOP手册, 交付中]
```

## 四、交付前自检清单

- [ ] 只讲一件事，标题能概括它；
- [ ] 五段齐全，且「验证」段能判断成功与否；
- [ ] 全文不出现「如上文」「同上」「它」这类无主指代；
- [ ] 字数在 300–800 之间（超了就拆）；
- [ ] `id` 唯一、`confidence` 已填、`l1` 只有一个值；
- [ ] 没有第二份副本躺在别的目录（单一归属）。

## 五、反例

| 反例 | 为什么错 |
| --- | --- |
| 一张卡里既有操作步骤又有事故检讨 | 两个层次混在一起，无法复用 |
| 「参考上文第 3 节」 | 切片后语义断裂，RAG 检索直接失效 |
| 2000 字长文不拆分 | 超出阅读与向量化粒度 |
| 只有「行动步骤」没有「验证」 | 无法判断操作是否成功 |
